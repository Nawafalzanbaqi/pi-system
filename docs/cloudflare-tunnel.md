# Public hosting with Cloudflare Tunnel + Let's Encrypt

This guide takes a project **generated by `scripts/new-project.sh`** and makes it
reachable from the **public internet** over HTTPS — **without opening a single
inbound port on the Pi**, and with a **real public Let's Encrypt certificate**
issued by **Caddy's own ACME** (not a manual Cloudflare certificate).

> **TL;DR.** Generate a project → copy it to the live Pi → run
> [`scripts/deploy-to-tunnel.sh`](../scripts/deploy-to-tunnel.sh). The script
> automates steps **b–g** below. This document explains every step (and the
> **one-time** Pi setup, **a**/**c**/**d**, the script expects to already exist)
> so you understand what is happening and can do it by hand if you prefer.

---

## How it works (and why no ports open)

```
                         (1) outbound only, no inbound ports
   ┌───────────┐   TLS    ┌────────────┐  encrypted tunnel  ┌──────────────────────┐
   │  Browser  │ ───────▶ │ Cloudflare │ ─────────────────▶ │  cloudflared (on Pi) │
   └───────────┘  https   │    edge    │   (Pi dials OUT)   └─────────┬────────────┘
                          └────────────┘                              │ localhost
                                                                      ▼
                                          ┌───────────────────────────────────────┐
                                          │ Caddy (the EXISTING reverse proxy)      │
                                          │  :80  ← ACME HTTP-01 challenge          │
                                          │  :443 ← real site, Caddy's LE cert      │
                                          └───────────────┬─────────────────────────┘
                                                          │ internal network
                                                          ▼
                                          your generated project (no host ports)
```

1. **`cloudflared`** runs on the Pi and makes an **outbound** connection to
   Cloudflare's edge. There is **no inbound listener** — the Pi's firewall stays
   default-deny and **80/443 remain closed to the public internet**. (Caddy still
   binds `80`/`443` on the Pi, but only `localhost`/the LAN can reach them; the
   public can't.)
2. Cloudflare's edge accepts the public HTTPS request and pushes it **down the
   tunnel** to `cloudflared`, which forwards it to **Caddy on `localhost`** — the
   same Caddy that already fronts the platform. **No second proxy, no separate TLS
   terminator.**
3. Caddy serves the site on **`:443` with its own Let's Encrypt certificate** and
   answers Let's Encrypt's **HTTP-01 challenge on `:80`** — both reached *through
   the tunnel*, so the certificate is issued and renewed with **no open inbound
   port**.

**Why Caddy still gets a Let's Encrypt cert even though Cloudflare also has one.**
With a Cloudflare Tunnel the browser always sees Cloudflare's edge certificate
(that's unavoidable — the connection terminates at Cloudflare first). Caddy's
Let's Encrypt certificate secures the **edge → Pi** hop end-to-end (Cloudflare
"Full (strict)"), so traffic is encrypted with a **publicly-trusted** certificate
the whole way and **no plaintext ever leaves the Pi**. This is exactly the
constraint we want: TLS is **only** Caddy's built-in ACME — we never install a
Cloudflare origin certificate by hand.

## Prerequisites

- A **domain you control in Cloudflare** — added to your Cloudflare account, with
  Cloudflare as its authoritative nameservers (the zone is "Active"). This is the
  `BASE_DOMAIN`. **It must be a real Cloudflare-managed domain** or the public
  name will never resolve to the tunnel.
- The **live Pi** running the platform (`./scripts/start-proxy.sh` is up).
- Your **dev machine** with this repo, where you generate projects. On Windows,
  run the shell commands and the helper script from **Git Bash** or **WSL** (they
  provide `ssh`/`scp`/`rsync`).
- SSH access to the Pi.

Throughout, replace the placeholders:

| Placeholder | Meaning | Example |
| ----------- | ------- | ------- |
| `<BASE_DOMAIN>` | your Cloudflare domain | `example.com` |
| `<SUBDOMAIN>` | the project's public subdomain | `shop` |
| `<PROJECT>` | the generated project / service name | `shop` |
| `<PI_USER>@<PI_HOST>` | SSH login for the Pi | `pi@raspberrypi.local` |
| `<PI_PROJECT_DIR>` | where this repo lives on the Pi | `/home/pi/pi-system` |
| `<ACME_EMAIL>` | e-mail for Let's Encrypt | `you@example.com` |

## a. Generate a project to expose

Any project with a **web-facing component** can be tunnelled (`nextjs-app`, the
`fullstack` frontend, or a `dotnet-api`). A good end-to-end test is the
**`ecommerce`** preset — it's a `fullstack` shape that composes **both** current
feature modules (`i18n-bilingual` + `content-admin`):

```bash
# On your dev machine, from the repo root:
./scripts/new-project.sh --name shop --preset ecommerce --subdomain shop
```

What matters for public hosting:

- **`--subdomain <SUBDOMAIN>`** — this is the public name. The project will be
  served at `https://<SUBDOMAIN>.<BASE_DOMAIN>`. If you omit it, it defaults to
  the project name. (DNS label rules: lowercase `[a-z0-9-]`, no leading/trailing
  `-`.)
- `--name`, `--preset`/`--base`, `--db`, `--locale` — as usual (see the main
  [README](README.md#scaffold-a-project)). The generator already:
  - writes the project into `services/<PROJECT>/`,
  - appends a Caddy site block `<SUBDOMAIN>.{$BASE_DOMAIN:localhost}` with
    `tls {$CADDY_TLS:internal}` — **this is the line that becomes public Let's
    Encrypt automatically** once `ACME_EMAIL` is set (step **f**), and
  - appends an **empty** `# >>> PROJECT: <PROJECT> >>>` section to `.env.example`.

> Test it locally first if you like (`./scripts/project.sh up shop`,
> browse `https://shop.localhost`). The **same** project files run unmodified on
> the public tunnel — only `.env` differs. See *Verifying it works unmodified* at
> the end.

## b. Copy the project to the live Pi

Send the generated `services/<PROJECT>/` folder to the repo on the Pi. Use
`rsync` (incremental) or `scp` over SSH:

```bash
# rsync (preferred — only sends changes):
rsync -az -e "ssh -p 22" \
  ./services/<PROJECT>/ \
  <PI_USER>@<PI_HOST>:<PI_PROJECT_DIR>/services/<PROJECT>/

# or scp:
ssh <PI_USER>@<PI_HOST> "mkdir -p <PI_PROJECT_DIR>/services/<PROJECT>"
scp -r ./services/<PROJECT>/. \
  <PI_USER>@<PI_HOST>:<PI_PROJECT_DIR>/services/<PROJECT>/
```

The project's **Caddy site block** lives in *your dev machine's*
`services/proxy/Caddyfile` (the generator put it there). The Pi has its own
Caddyfile, so that block must also be added on the Pi — `deploy-to-tunnel.sh`
copies it across surgically (begin/end markers), or add it by hand in step **f**.

> `.env` is git-ignored and **not** copied. Any project-specific secrets (e.g.
> the `CMS_*` values that `content-admin` needs) must be set in the **Pi's**
> `.env` — see step **g**.

## c. One-time: install & configure `cloudflared` on the Pi

This is **per-Pi setup**, done once — not per project. Run it on the Pi.

### Install the daemon (ARM64)

The Pi 5 is **ARM64**, so use the `arm64` build. Pin a known release tag (per the
platform's "never `latest`" rule) and update it deliberately:

```bash
# On the Pi. Replace the version with the latest stable release tag.
CFD_VERSION=2024.12.2
sudo curl -L -o /usr/local/bin/cloudflared \
  "https://github.com/cloudflare/cloudflared/releases/download/${CFD_VERSION}/cloudflared-linux-arm64"
sudo chmod +x /usr/local/bin/cloudflared
cloudflared --version          # verify
```

> `cloudflared` is a security-relevant edge daemon — re-check the
> [releases page](https://github.com/cloudflare/cloudflared/releases)
> periodically and bump `CFD_VERSION`.

### Authenticate to Cloudflare

```bash
cloudflared tunnel login
```

This prints a URL — open it in any browser, log in, and **authorize the zone**
for `<BASE_DOMAIN>`. It writes a certificate to `~/.cloudflared/cert.pem` (this
authorizes creating tunnels and DNS records for that zone).

### Create the tunnel

```bash
cloudflared tunnel create pi-system
```

This creates a tunnel named `pi-system` and writes its **credentials file** to
`~/.cloudflared/<TUNNEL_ID>.json`. Note the `<TUNNEL_ID>` it prints.

### Place the credentials where the service can read them

```bash
sudo mkdir -p /etc/cloudflared
sudo cp ~/.cloudflared/<TUNNEL_ID>.json /etc/cloudflared/
sudo cp ~/.cloudflared/cert.pem        /etc/cloudflared/   # for DNS routing as root/service
```

### Write the tunnel config (`/etc/cloudflared/config.yml`)

This is a **catch-all** ingress — it routes **any** hostname pointed at this
tunnel to the local Caddy, so you **never** edit it per project:

```yaml
# /etc/cloudflared/config.yml
tunnel: <TUNNEL_ID>
credentials-file: /etc/cloudflared/<TUNNEL_ID>.json

# Don't auto-create DNS — we add records explicitly (step e), so a typo never
# rewrites an existing record.
ingress:
  # 1) Let's Encrypt HTTP-01 challenge -> Caddy's HTTP listener (:80).
  #    Caddy answers the challenge itself here; it is NOT proxied to the app.
  - path: /.well-known/acme-challenge/*
    service: http://localhost:80

  # 2) Everything else -> Caddy's HTTPS listener (:443), where Caddy serves the
  #    real Let's Encrypt cert. End-to-end TLS = Cloudflare "Full (strict)".
  #    noTLSVerify keeps the loopback hop simple: it's already inside Cloudflare's
  #    encrypted tunnel and never leaves the Pi. Caddy routes to the right site by
  #    the (preserved) Host header.
  - service: https://localhost:443
    originRequest:
      noTLSVerify: true

  # 3) Required catch-all.
  - service: http_status:404
```

### Run it as a service (auto-restart on boot)

```bash
sudo cloudflared service install      # reads /etc/cloudflared/config.yml
sudo systemctl enable --now cloudflared
systemctl status cloudflared          # should be "active (running)"
cloudflared tunnel info pi-system     # should show a healthy connection
```

`cloudflared` now holds an outbound connection to Cloudflare and is ready to
serve **any** hostname you route to it. **No inbound port was opened.**

## d. One-time: link the tunnel to Caddy

Two pieces, both already prepared in this repo and both **one-time**:

1. **The Caddy `http_port` global block.** `services/proxy/Caddyfile` now starts
   with a global options block:

   ```caddy
   {
       http_port 80
   }
   ```

   This pins the port Caddy serves the **ACME HTTP-01 challenge** (and the
   HTTP→HTTPS redirect) on — exactly the `http://localhost:80` the tunnel forwards
   the challenge to (step **c**, ingress rule 1). `80` is Caddy's default, so this
   changes nothing for local use; it just makes the tunnel contract explicit. If
   your Pi's Caddyfile predates this change, add that block at the top (above the
   first site block) — `deploy-to-tunnel.sh` does this for you, idempotently.

2. **The `cloudflared` ingress → Caddy** (the `config.yml` from step **c**). The
   catch-all sends the challenge to `:80` and the site to `:443`, so Caddy — the
   **existing** reverse proxy — answers the tunnel "in addition to" its normal
   `localhost`/LAN traffic.

That's the entire wiring. Because the ingress is a catch-all and the per-site TLS
mode is env-driven, **adding a project never touches `cloudflared` or the global
Caddy config again** — only a DNS record and the project's own site block change.

> **`Always Use HTTPS`.** Cloudflare may 301 plain-HTTP at the edge before it
> reaches the tunnel. Let's Encrypt's HTTP-01 validator **follows redirects**, and
> our ingress matches `/.well-known/acme-challenge/*` on **either** port, so
> issuance still works. If a cert ever fails to issue, see *Troubleshooting*.

## e. Add the Cloudflare DNS record (per project)

Point `<SUBDOMAIN>.<BASE_DOMAIN>` at the tunnel. `cloudflared` does this for you
via the Cloudflare API (using the `cert.pem` from step **c**) — **no manual
dashboard editing, no manual CNAME**:

```bash
# On the Pi:
cloudflared tunnel route dns pi-system <SUBDOMAIN>.<BASE_DOMAIN>
```

This creates a **proxied** (orange-cloud) `CNAME` →
`<TUNNEL_ID>.cfargotunnel.com`. The orange cloud is what makes Cloudflare
terminate the public TLS and push traffic down the tunnel. (If it ever shows as
"DNS only"/grey, switch it to **Proxied** in the dashboard.)

> `<BASE_DOMAIN>` must be a zone you authorized in step **c**, or this command
> fails. Re-running it for an existing record is harmless.

## f. Let's Encrypt validation in the project's Caddy block

**There is nothing to issue by hand.** The Caddy site block the generator wrote
already reads its TLS mode from the environment:

```caddy
# >>> pi-system project: shop >>>
shop.{$BASE_DOMAIN:localhost} {
    tls {$CADDY_TLS:internal}
    encode zstd gzip
    reverse_proxy shop-web:3000
}
# <<< pi-system project: shop <<<
```

`proxy.compose.yml` derives `CADDY_TLS` from `ACME_EMAIL`:

- `ACME_EMAIL` **blank** → `CADDY_TLS=internal` → Caddy's local CA (the local
  default).
- `ACME_EMAIL` **set** (a real e-mail) → `CADDY_TLS=<ACME_EMAIL>` → Caddy obtains
  a **public Let's Encrypt** certificate via the **HTTP-01 challenge**, served on
  `:80` and reached through the tunnel.

So "adding Let's Encrypt" = **setting `BASE_DOMAIN` + `ACME_EMAIL` in the Pi's
`.env`** (next step). Make sure this project's site block exists in the **Pi's**
`services/proxy/Caddyfile`; if you copied only the project folder in step **b**,
append the block delimited by
`# >>> pi-system project: <PROJECT> >>>` … `# <<< pi-system project: <PROJECT> <<<`
from your dev Caddyfile to the Pi's. (`deploy-to-tunnel.sh` does this for you.)

## g. Start the project on the Pi with live ENV, and test

On the **Pi**, set the public values in `.env` (root of the repo):

```bash
# <PI_PROJECT_DIR>/.env
BASE_DOMAIN=<BASE_DOMAIN>
ACME_EMAIL=<ACME_EMAIL>
```

> Setting these flips **every** site (Portainer, status, your project, …) to
> public Let's Encrypt. Run `./scripts/check-secrets.sh` and the
> [pre-exposure checklist](README.md#pre-exposure-security-checklist) first.
> Also set any **project secrets** the project needs in `.env` — e.g. for the
> `content-admin` module: `CMS_KEY`, `CMS_SECRET`, `CMS_ADMIN_EMAIL`,
> `CMS_ADMIN_PASSWORD`, `CMS_DB_PASSWORD` (copy the `# >>> PROJECT: <PROJECT> >>>`
> section from `.env.example` and fill it in).

Then bring it up (Caddy must reload to serve the new block **and** pick up the new
`.env`, so it requests the certificate):

```bash
cd <PI_PROJECT_DIR>

# If the project uses a shared DB, start it (skip for --db none):
./scripts/db.sh <engine> up

# Recreate Caddy with the new .env (BASE_DOMAIN/ACME_EMAIL) + reload the Caddyfile:
./scripts/start-proxy.sh
docker exec ${COMPOSE_PROJECT_NAME:-pi-system}_caddy caddy reload --config /etc/caddy/Caddyfile

# Build + start the project (plus any module fragments, e.g. content-admin's CMS):
./scripts/project.sh up <PROJECT>
```

**Test it** (from anywhere — your laptop, your phone on cellular, …):

```bash
# Follow Caddy as it obtains the certificate the first time:
docker logs -f ${COMPOSE_PROJECT_NAME:-pi-system}_caddy   # look for "certificate obtained successfully"

# DNS resolves to Cloudflare (proxied):
dig +short <SUBDOMAIN>.<BASE_DOMAIN>

# Real, publicly-trusted certificate (NOT self-signed), HTTP/2, 200/redirect:
curl -I https://<SUBDOMAIN>.<BASE_DOMAIN>

# Inspect the chain the edge serves (issued by a public CA, valid):
echo | openssl s_client -connect <SUBDOMAIN>.<BASE_DOMAIN>:443 \
  -servername <SUBDOMAIN>.<BASE_DOMAIN> 2>/dev/null | openssl x509 -noout -issuer -subject -dates
```

Then open **`https://<SUBDOMAIN>.<BASE_DOMAIN>`** in a browser — you should get
the project with a valid padlock (for the `ecommerce` test, the bilingual
Arabic-first home page; it redirects `/` → `/ar`). Confirm with `docker ps` on
the Pi that **only Caddy** publishes host ports and they are **not** reachable
from the public internet (they're served only through the tunnel).

## The automated path: `scripts/deploy-to-tunnel.sh`

Once the **one-time** setup (**a** generate, **c** cloudflared, **d** Caddy
`http_port`) is in place, the per-project steps **b–g** are one command from your
dev machine:

```bash
# Edit the CONFIG block at the top of the script (or pass via env vars):
#   PI_HOST, PI_USER, PI_SSH_PORT, PI_PROJECT_DIR, BASE_DOMAIN, TUNNEL_NAME

./scripts/deploy-to-tunnel.sh --name shop --subdomain shop --email you@example.com

# Override connection details inline without editing the file:
PI_HOST=10.0.0.5 BASE_DOMAIN=example.com \
  ./scripts/deploy-to-tunnel.sh --name shop --subdomain shop --email you@example.com
```

It will: copy the project to the Pi (b) · verify `cloudflared` + the tunnel exist,
refusing to continue if the one-time setup is missing · ensure the Caddy
`http_port` block and the project's site block on the Pi (d, f) · `cloudflared
tunnel route dns` for the subdomain (e) · set `BASE_DOMAIN`/`ACME_EMAIL` in the
Pi's `.env` (backing it up first) · reload Caddy and start the project (g). Pass
`--start-db` to also start the project's shared database engine. It never prints
secret values and backs up any file it edits.

## Troubleshooting

| Symptom | Likely cause / fix |
| ------- | ------------------ |
| Name doesn't resolve | DNS record missing or grey-cloud. Re-run `cloudflared tunnel route dns pi-system <SUBDOMAIN>.<BASE_DOMAIN>`; ensure it's **Proxied**. DNS can take a minute. |
| **Error 1033 / tunnel error** | `cloudflared` isn't running or unhealthy: `systemctl status cloudflared`, `cloudflared tunnel info pi-system`. |
| **502 / 521 / 523** | Caddy or the project is down on the Pi: `docker ps`, `./scripts/start-proxy.sh`, `./scripts/project.sh status <PROJECT>`. The tunnel forwards to `localhost:443`, so Caddy must be up. |
| **525 (SSL handshake failed)** | Cloudflare can't TLS-handshake the origin. Ensure ingress rule 2 is `https://localhost:443` with `noTLSVerify: true` and Caddy is listening on 443. |
| Certificate won't issue | Watch `docker logs <…>_caddy`. Confirm `ACME_EMAIL` is set and `CADDY_TLS` is the e-mail (`docker exec <…>_caddy env | grep CADDY_TLS`). Confirm the `path: /.well-known/acme-challenge/*` ingress rule exists. If "Always Use HTTPS" interferes, add a Cloudflare **Configuration Rule** that disables it for `/.well-known/acme-challenge/*`. |
| Let's Encrypt **rate limit** | While testing, point Caddy at staging by adding `acme_ca https://acme-staging-v02.api.letsencrypt.org/directory` to the global options block, then remove it for production (delete the staging cert from the `caddy_data` volume after). |
| Redirect loop | Don't point the tunnel at `http://localhost:80` for *all* traffic — Caddy would 308→HTTPS forever. Use the split ingress in step **c** (challenge→`:80`, site→`:443`). |

## Verifying it works unmodified (local test → public tunnel)

The whole point of the env-driven design: **the project you tested locally runs
on the public tunnel with zero changes to its files.**

- **Local:** `BASE_DOMAIN` blank → `localhost`, `ACME_EMAIL` blank → `internal`.
  The project answers at `https://<SUBDOMAIN>.localhost` with Caddy's **internal
  CA** certificate.
- **Public:** `BASE_DOMAIN=<BASE_DOMAIN>`, `ACME_EMAIL=<ACME_EMAIL>` in the Pi's
  `.env`. The **same** site block — `tls {$CADDY_TLS:internal}` — now resolves
  `CADDY_TLS` to your e-mail and Caddy switches that site to **public Let's
  Encrypt**, reached over the tunnel.

What's identical between the two:

- the project's `services/<PROJECT>/` folder (Dockerfiles, compose fragments,
  app code, module files) — **byte-for-byte**;
- the Caddy **site block** (`<SUBDOMAIN>.{$BASE_DOMAIN:localhost}` with
  `tls {$CADDY_TLS:internal}`);
- the database wiring (by service name, on `internal`), the no-host-ports posture,
  and the firewall rules.

What's different: **only `.env`** (`BASE_DOMAIN` + `ACME_EMAIL`) and **two
external facts** — a Cloudflare DNS record and the `cloudflared` daemon. So you
can confidently develop and test against `*.localhost`, then publish the exact
same artifact by setting two env vars and running one script.
